# Durable planning recovery design — issue #10

Planning remains a Vinext/React Cloudflare Worker with D1. Current API/MCP identity and exact owner isolation remain authoritative. This is source/local validation, not provisioning, deployment, production migration, real callback registration or Ticket execution. Existing auth, approval and runner code remains intact. Keep both locks unchanged; fresh isolated D1 for tests.

## Chosen architecture

Use a D1 per-target outbox and Worker scheduled handler. An in-memory timer loses retries on restart; Cloudflare Queues would require separately provisioned infrastructure. D1 is already the authoritative revision/claim storage and permits atomic guards. Request delivery and scheduled recovery share one bounded routine. Do not retain synchronous sleep/retry loops.

Extend jobs with recovery generation (default0), recoveries (default0), wake deadline, retry-after/cooldown, recovery reason and update timestamp. Persist `planning_deliveries` with owner, job_id, subscription_id, generation, event_id, status, attempts, next_attempt_at, delivery token/lease, last HTTP status, terminal reason and timestamps; unique job/subscription/generation and due indexes. Store callback secrets only in subscriptions, never in outbox or visible DTOs. A generated migration and matching Drizzle snapshot/journal describe the schema. No raw reapplication to existing D1.

## Delivery and subscription behavior

Initial events keep their existing event IDs; within a generation retries reuse exact event JSON/ID, enabling receiver deduplication. Recovery creates a new persisted generation event/ID with same Idea/job/revision payload. Outbox rows are created only for current queued jobs and active exact-project subscriptions. No subscription remains durable and visible as no_subscription, without consuming attempts or recovery budget. A new/refreshed subscription backfills current unfinished matching queued jobs, at most50 per immediate invocation; cron continues bounded backlog discovery. Refresh revives expired/unsubscribed targets but does not reset accepted targets or permanent/exhausted failures. Active planning claims suppress delivery.

Claim each due target through a conditional update with random token and 30-second delivery lease; attempts increment once on successful acquisition. Revalidate job generation/current Idea revision/queued status and active matching subscription before outbound; stop stale/done targets and invalidate their tokens. Complete the network result only under that token and job generation. Expired delivery leases may be reclaimed without generating a new event. Concurrent request/cron workers must not send the same leased row twice. A crash after receiver acceptance but before persistence yields a duplicate event ID after lease expiry; this is at-least-once delivery, never an exactly-once claim.

Each delivery invocation invalidates at most50 target rows total across job/subscription reasons, in stable order and within its optional owner/job request scope; later ticks continue the backlog. Acquisition checks independently suppress invalid rows before dispatch. Keep HTTPS OpenAI callback allowlist, redirect rejection, HMAC and rotation. One attempt has an8-second timeout. Retry network/timeout/429/5xx with exponential delays 30s,60s,120s,240s, bounded at5 attempts per target/generation. Permanent non4294xx, redirects, invalid callback/signing secret and oversized event stop with a sanitized reason.410 expires/removes the subscription and visibly terminates that target; other targets can continue. No target secret/URL, transport body or arbitrary error string appears in visible metadata. Summaries distinguish pending/retrying/accepted/partial/failed/no_subscription.

## Recovery lifecycle

An accepted event that produces no claim by5minutes gets a wake deadline; it may recover into a new generation to wake a disconnected consumer. An active planner owns a10-minute lease. Expired planner claims are released using token/status/lease/current revision CAS; old tokens cannot save, including when they race recovery. Persist reason `claim_expired` or `consumer_unclaimed`. Limit automatic recovery to3 generations; exhaustion leaves a visible failed/retryable job rather than a permanent planning spinner. Do not recover done/superseded jobs or active claims. Repeated polling is readonly. Scheduled work processes bounded discovery/recovery and at most20 outbound rows ordered by due time/id; overdue backlog remains persistent. Configure `*/1 * * * *` in the generated Worker configuration; local scheduled integration calls the real built handler. No deploy is implied.

Manual planning POST verifies owner/same-origin/current Idea and CAS. Active unexpired claim returns its metadata without reset. For expired claim, consumer timeout or terminal failures it can start/reset one generation, subject to a60-second cooldown; duplicate/concurrent manual retries cannot multiply generations. A queued pending/backoff/accepted-before-wake job does not reset on every click. Manual retry can reset automatic recovery budget after exhaustion. New current revision jobs remain idempotent; completed result is unchanged. All claim/save predicates use status, token, strictly future lease and exact revision guards atomically. Clock equality counts as expired.

A stored expired planning state is displayed as expired/retryable before cron catches up. Show active lease expiry, next retry, exhausted/permanent reason and an enabled manual recovery action once eligible. Fallback missing job metadata cannot permanently disable the only action.
